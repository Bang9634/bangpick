# 0003 — 파일 저장소와 비동기 재구성 작업 분리

- 상태: 채택
- 날짜: 2026-11-12
- 근거: 사용자가 제안된 등록·업로드·재구성·검수·조회 흐름에 동의하고 초기부터 오브젝트 스토리지를 사용하는 방향을 제시함.

## 결정

백엔드는 매물 소유권·접근 권한·업로드 허가·자산 메타데이터·작업 상태를 관리합니다. 원본과 결과 파일은 별도 저장 책임으로 분리하고, Worker는 준비될 때 대기 작업을 가져와 입력 파일을 읽고 결과물을 저장합니다. 브라우저가 GPU Worker에 직접 영상을 업로드하는 구조는 사용하지 않습니다.

서비스 통합 개발 초기부터 오브젝트 스토리지를 사용합니다. 백엔드가 제한된 업로드 권한을 발급하고 브라우저가 저장소에 직접 업로드하는 방식을 기본 방향으로 합니다. 백엔드는 업로드 확인 후 작업을 등록합니다. Worker는 결과물을 저장하고 완료를 보고하며, 검수 후 공개한 결과만 투어에 연결합니다.

완성된 투어 파일은 GPU PC 밖에 보관하여 Worker가 꺼져도 기존 투어를 조회할 수 있게 합니다. 원본 영상과 학습 중간 결과는 공개 결과와 접근 범위를 구분합니다. 학습 완료와 공개 상태를 분리합니다.

## 초기 개발과 배포

초기에는 일반 폴더로 시작하는 대안도 검토했으나, 웹과 팀 GPU PC 간 연동 및 향후 클라우드 이전을 고려해 별도의 폴더 기반 업로드 중계 기능을 먼저 개발하지 않습니다. 로컬 폴더는 Worker의 임시 작업 공간이나 개별 테스트 용도로만 사용할 수 있습니다. 스토리지 공급자는 팀 계정·크레딧·요금·필요 기능을 확인한 뒤 선택하며, 외부 자원을 생성한 상태는 아닙니다.

배포 시 웹·백엔드와 GPU Worker는 서로 다른 장비에서 실행할 수 있고 공통 파일 저장소에 API로 접근합니다. DB에는 자산 ID와 저장 키·크기·형식·버전 등 메타데이터를 저장합니다. 파일 바이너리나 만료되는 서명 URL을 영구 식별자로 사용하지 않습니다.

## 영향

권한·업로드 완료 확인·작업 점유와 재시도·결과 검수·고아 파일 정리가 필요합니다. 저장소 공급자를 바꾸더라도 자산 ID와 작업 계약을 유지하도록 설계합니다. 로컬 업로드 중계에서 직접 업로드로 바뀌면 업로드 API와 프론트 경로에도 변경이 필요할 수 있습니다.

이 문서는 설계 채택 기록이며 서버·버킷·API가 구현되거나 외부 자원이 생성된 기록은 아닙니다.
